## 2. Evidence categories and decision rules

Every assertion records both a result (`PASS`, `FAIL`, `BLOCKED`, or `NOT_RUN`) and the actual evidence category. Categories may be combined for one case but must remain separately identifiable.

| Category | What counts | What it cannot establish |
|---|---|---|
| REAL_GPT | Authorized, configured GPT provider actually receives the synthetic request through fixed DSH `ctx.llm`; its returned structured call is executed through `ctx.tools`; correlated route and outcome evidence exists | A hand-built call, mocked stream, model-name label, replay, or access to GPT in this development chat is not provider proof |
| REAL_HOST_HTTP_SQLITE | Supported fixed DSH profile, real business login/Cookie, actual HTTP handlers and on-disk SQLite, independently queried | Real GPT choice or actual browser rendering |
| REAL_UI | Browser/native UI attached to that running Host, with actions and observed rendered results correlated to requests | A source grep, HTML generator, static screenshot, or fixture-backed UI cannot prove real GPT |
| CONTROLLED_FIXTURE | Explicit synthetic model stream/adapter, deterministic clock/barrier/failure, or direct service/tool invocation; disclose which layers remain real | Provider availability, provider-specific normalization, real permission transport, or real timing unless separately exercised |
| STATIC | Source/types/schema/import/config/hash/build inspection | Authentication, race handling, persistence, UI behavior, or a live provider call |

A passing fixture is useful evidence for its stated behavior, not a live integration pass. Deliberately injected failures can PASS their expected rejection assertion. A required check that could not execute is BLOCKED with the actual dependency; an unattempted check is NOT_RUN. An observed behavior contrary to this contract is FAIL. Do not classify missing credentials as a product FAIL unless the error handling itself is wrong, and do not classify an implementation defect as an environmental BLOCKED.

T01, T02, and the real-model portion of T08 require REAL_GPT plus REAL_UI and REAL_HOST_HTTP_SQLITE evidence. T03–T07 may use a controlled model selector to force adversarial/error cases, but identity transport and object effects need real Host/HTTP/SQLite checks as specified below. Their model dimension must then say CONTROLLED_FIXTURE. At least one real provider call is necessary for unit completion, and does not alone satisfy both T01 and T02. - `packages/core/tool-executor-native/src/index.ts`: the native executor uses the shared pipeline. `packages/core/tools/README.md` and `docs/cookbook/adding-a-tool.md`: effect-owned registration, output schemas, structured failures, conditional selection, and cancellation. - `packages/llm/llm/README.md` and `src/error.ts`: real streaming, exact route capture, terminal failures, and provider codes. These are local fixed-source observations, not claims about a newer upstream release.

Acceptable minimal integration: a KnowledgeOS transport authenticates the actual business request, creates an immutable server-owned binding to that verified session/service/account, and surrounds the awaited native `ctx.tools.execute({ calls, signal, ... })` dispatch with request-local server context (for example `AsyncLocalStorage.run`). Registered tool handlers obtain that binding outside `args`, re-resolve the current session through an identity port, and pass a freshly trusted actor into the business use case. The binding must retain sufficient server-only session provenance to revalidate expiry/revocation; saving only `{ userId, role }` at request start is insufficient. The reference must originate from verified credentials, not a submitted session ID.

An alternative is a server-owned map keyed by an actual DSH Agent object, with that Agent securely and exclusively bound to the authenticated business session. It must prove the same revalidation, scope, isolation, and disposal properties. `agent`, `sessionId`, `callId`, `rootCallId`, `toolSet`, and `exec.token` are execution/correlation identities, not business authentication. Do not fabricate an Agent-shaped object from model JSON, use a shared owner Agent as the user, mutate global `currentActor`, attach identity to prompt/tool arguments, or treat a predictable identifier as authority. An Agent scope or admitted tool set never replaces current ACL.

Required identity tests:

1. A real login succeeds; no Cookie, invalid Cookie, owner-only Cookie, expired/revoked session, and inactive user all fail as business authentication. A normal business Cookie still cannot access owner status/RPC/Shell/files/plugins/Session attachments. Existing origin, authority, Fetch-Metadata, and mutation-header checks also cover the new route.
2. At the external JSON boundary, injected `user_id`, `actor`, `actor_id`, `role`, `owner_id`, `owner_user_id`, `service_id`, `space_id`, or purported authorization/session token is rejected as unsupported input. Within natural-language instructions or object text, such claims have no authority. No identity/credential field appears in the allowed tool schemas. A missing trusted execution binding fails closed even if a syntactically valid call names an existing object.
3. Interleave two real business sessions with barriers before model completion and tool dispatch; each can act only on its own authorized targets. Duplicate/colliding model call IDs cannot cross-bind users. A call started by A must never adopt B after a UI account switch; original-session invalidation rejects A's pending call. Returned/cached results must not render into B's account view.
4. Revalidate the originating session after model latency, after an approval/tool-policy/lock wait, and at the mutation boundary. Cover logout in another client, absolute session expiry, account inactivity, and replacement/revocation of the originating session. A cached SessionActor must not survive those changes. Use a current server clock, not request-start or client/model time.
5. Test missing context, parallel requests, cancellation, thrown tools, completion, and reload/disposal for context leakage. A later unbound dispatch must not inherit an earlier user's context. Prove native async context propagation in the actual composed executor; do not infer it from an isolated AsyncLocalStorage example. Other processes, PTC, queues, and restored Agents need explicit secure rebinding if used; they are not implicitly supported.
6. Keep authority out of model-visible arguments, output metadata, logs, and error details. If `agent`/`log` are omitted, upstream documents that root Session call/result logging is omitted. The candidate must supply a correlated, access-controlled request/tool/result record appropriate to its actual integration; do not claim upstream automatic logging in that case. Model-visible inputs must remain reconstructable under the upstream recording policy without exposing secrets or private Session APIs to business users.

The adapter owns DSH/context mechanics; the business/authorization code owns current user, object, revision, and action rules. Do not import a DSH service or ambient request context into the pure authorization function. A pre-execute guard alone is insufficient when work can wait afterwards.

## 5. Delayed execution and authorization linearization (T03/T04)

Use synthetic admin/A/B accounts and separate real login contexts, plus personal objects and project objects with explicit read/edit grants. Membership alone grants no object action; edit does not imply read, delete, or manage_share. Use objects with unique synthetic title/body sentinels to detect leaks. Include a project object created by the member whose membership will expire, reproducing FND-004 R1.

Observe these distinct points: authenticated request admitted; model call/call arguments prepared; native policy/guard complete; business storage transaction acquires its lock; fresh authorization/version checks; commit or denial; result publication. A controlled barrier in a test adapter/clock/storage seam may pause work; mark it CONTROLLED_FIXTURE and demonstrate that the subsequent production dispatch and SQLite path are real. Do not expose a production HTTP `force_fail`, arbitrary SQL, clock, or actor override. No new barrier/test code is authorized by this document-writing assignment.

Required subcases, for read and update wherever applicable:

- D1: Grant is initially effective, revoke it by the authorized real HTTP endpoint before releasing the prepared tool. Expect safe 404 NOT_FOUND/tool denial, no body/title in any result, and unchanged object/revision. Verify current DB grant history independently.
- D2: Set a short real grant lifetime, prepare while valid, and release at/after its recorded absolute expiry. Prove `valid_from <= now < expires_at`, denial at equality, and future-valid grants denied. A deterministic boundary clock test complements an observed elapsed-time integration; disclose the clock seam.
- D3: Retain read/edit grants but expire/revoke project membership before release. Both recipient and project-object creator lose access; explicit user grants, project-subject grants, and admin role do not preserve access. Prove normal positive controls with effective membership plus the exact action grant.
- D4: Perform a non-secret session invalidation/expiry/inactive-account transition after preparation. Expect business 401 SESSION_EXPIRED/AUTH_REQUIRED before object output or mutation, even though the prepared operation and actor once existed.
- D5: Wait after an early authorization check, including a real SQLite lock wait if used. Commit the revocation on another connection before the update's final authorization/transaction can proceed; release the wait. Expect denial and no write. Passing only D1 at the HTTP entrance does not establish D5.
- D6: Complete an allowed update, revoke read/edit or expire membership, then replay the same key. Expect current authorization denial; the persisted original receipt must not leak protected body/title/revision. Likewise revalidate access before releasing delayed read/model output; suppress newly restricted content. Data already delivered while authorized is not claimed to be retractable.
- D7: Regrant through a new active grant and deliberately submit a new allowed operation; preserve old revoked grant history. This positive control proves denial followed real authority changes rather than a globally broken tool. It must not automatically replay cancelled or rejected prepared work.

Define race expectations by transaction ordering, not by a universal 'revocation always wins' assertion. If revocation is committed before the mutation's final serialized authorization point, update must deny. If an already-authorized write commits before revocation can acquire its lock, record that valid ordering and verify all later operations deny. Capture an ordering trace and use a fresh clock after waits. Permission, session, object lifecycle, expected revision, idempotency claim/result, and mutation must be consistent at the commit boundary; no await gap after the decisive check may permit a stale-authority commit.

## 6. Exact idempotent result and revision oracle (T02/T05/T06)

Freeze the accepted key syntax/location, semantic request normalization, key namespace, retained result fields, and transaction protocol in the candidate design before execution. Keys are not authorization. Scope the durable operation to the authenticated service/user and the declared update operation family so another user/service cannot replay, observe, or poison its result. Within that namespace, bind the semantic fingerprint to tool/action, object, expected revision, and every effective patch field; exclude transport call/request IDs so a retry can have new transport correlation. Changing the target object must not silently create a new namespace for the same update key. Only documented equivalent JSON ordering may normalize identically; do not silently erase meaningful whitespace or patch differences.

Expected sequence and independent oracle:

1. Snapshot authorized object O at revision r with title/body/created_at/updated_at and operation-row count scoped to this actor/service/key. Submit K, O, expected r, patch P. Success yields committed result R at r+1 and one successful durable operation. Independent SQL/GET agree with P and R; title/body not patched and created_at are preserved. Unrelated objects do not change.
2. Retry identical semantic inputs under a new transport request/call ID. Return exactly R's business payload: same object ID, committed revision, title/body or declared result projection, original mutation timestamp, and stable operation identity. New envelope request/server-time or explicit replay metadata may differ only if outside the frozen business result. A second revision increment, a second committed mutation, or a newly generated 'original' mutation timestamp is FAIL.
3. Independently make a different authorized edit to O at r+2 with a different key. Replay original K with original expected r and P. With current permission still effective, return original R at r+1, not current O at r+2 and not a stale-version conflict. The database remains r+2. This distinguishes persisted exact-result replay from rebuilding a result from the latest object.
4. Repeat after a genuine Host stop/restart using the same database and fresh valid login where needed. Durable identity scoping must allow the same user's authorized retry across login sessions, without trusting a supplied user ID or reviving an expired session. An in-memory Map cannot satisfy this check.
5. Reuse K with changed body, title, expected revision, or target object within the same authenticated update operation namespace. Return 409 IDEMPOTENCY_CONFLICT, never overwrite R or mutate either object. Use readable/authorized targets for this assertion so authorization secrecy does not mask the conflict. The namespace may isolate different actors/services or unrelated operation families; it must not turn different parameters of this update operation into an allowed same-key write.
6. Send simultaneous same-key/same-input requests: exactly one commit, callers obtain R after bounded settlement or a documented retryable in-progress response followed by R. Same-key/different-input competitors cannot both commit. Independent SQL queries must filter by the tested operation key and scope, not substitute a whole-table count.
7. Lose the first HTTP response after the local commit using a controlled transport fault, then retry K. Recover R without duplicate write. Inject a failure between mutation and receipt persistence using the actual transaction path in an isolated DB: either both commit or both roll back; no mutation without its durable replay result and no successful receipt without mutation. Record uncertainty if the harness cannot establish the commit point.
8. A different/unauthenticated/expired session or actor with revoked access cannot obtain R, even if K is known. Current authentication/authorization precede protected replay disclosure. If the tool returns object content, require current read permission as well as permission for its mutation; edit-only grants cannot become a body-read bypass.
9. Distinguish replay from a new operation: a fresh K2 with stale expected r after O advanced is 409 REVISION_CONFLICT. No body/title/revision/timestamp changes and no successful receipt. Validate missing, non-integer, non-positive revision and empty/missing key as input errors before side effects. Hidden targets return safe NOT_FOUND rather than leaking a version or prior key's existence.

Use a separate read-only SQLite connection for the oracle and explicit statements/parameters against the candidate's actual schema. Persist only synthetic projections, counts, and safe receipts in evidence. Storage/key uniqueness and transaction behavior require runtime evidence, not an index-name/source grep. A minimal FND-005 idempotency table is sufficient; this does not demand FND-006 jobs/outbox.

## 7. Error classification, cancellation, and unknown outcomes (T07)

The following are independent semantic classes. Except for the explicitly required application codes, candidate-specific spelling/HTTP mapping must be frozen before the run. Preserve a safe machine-readable upstream cause and phase; do not branch on English message text or collapse all failures into 'AI failed'. Provider failures never become business-login 401s, and business permission denial never becomes a provider-auth error.

| Stimulus / fixed-upstream signal | Expected observable classification |
|---|---|
| No selected GPT route; selected provider adapter unavailable (`NO_ADAPTER`) | MODEL_NOT_CONFIGURED/configuration-unavailable class, no alternate provider call |
| Selected route has no credential (`MISSING_CREDENTIAL`, or absent credential store) | Credential-missing class distinct from route absence; no leaked credential references/raw headers |
| Malformed or rejected credential (`INVALID_CREDENTIAL`, `AUTH`; provider permission rejection) | Invalid-credential/provider-authorization class, distinct from missing credential and business ACL |
| Exhausted allowance (`QUOTA`, relevant `ACCOUNT_QUOTA`) | Quota-exhausted/blocked; no success, invented balance, fallback model, or unbounded retry |
| Rate limit (`RATE_LIMIT`) or local call budget | Rate/local-budget class distinct from quota; safe retry guidance only when known |
| Unavailable exact model (`UNKNOWN_MODEL`, `MODEL_UNSUPPORTED`, structured provider missing-model response) | Model-not-found/unsupported class; an unlisted catalog entry alone is not proof a provider rejected it |
| Provider deadline (`TIMEOUT`), distinct tool deadline (`TOOL_TIMEOUT`) | Timeout with correct phase; tool-body timeout requires cooperative handling and actual timeout policy/configuration |
| User cancellation / `ABORTED`, or `ABORTED_BEFORE_DISPATCH` | Cancelled with correct phase; stopped work cannot later publish success or initiate a late mutation |
| Provider/network/malformed/truncated response (`TRANSPORT`, `SERVER`, `MALFORMED_RESPONSE`, `STREAM_CLOSED`, etc.) | Model/transport/protocol error with safe cause, no fabricated complete tool arguments or business success |
| Business session missing/expired/revoked | 401 AUTH_REQUIRED/SESSION_EXPIRED; no provider request for a request already rejected at admission |
| Cross-user/private or revoked object, membership expired | Safe 404 NOT_FOUND externally; structured tool denial internally, no existence/title/body leak |
| Authorized new-key stale revision | 409 REVISION_CONFLICT |
| Authorized same-key different semantic request | 409 IDEMPOTENCY_CONFLICT |
| Wrong schema/unknown or disallowed tool | Input/tool-rejected class before side effects, never SQL/path/Shell execution |
| Storage busy/unavailable or commit state unconfirmed | Storage failure or OPERATION_OUTCOME_UNKNOWN as applicable; no claim that an unverified commit succeeded or rolled back |

Fixtures must exercise actual terminal stream failures/typed error normalization through the candidate adapter/use case and UI, not merely throw the desired final app code from a fake business service. Retain both input upstream code and resulting app class in safe evidence. Upstream `HarnessError` identity preserves expected tool error codes; returning `{ error: ... }` as a nominal canonical success is not enough. A provider HTTP status alone may be ambiguous (for example 429 quota vs rate); require structured cause evidence or report an unknown class honestly.

Cancel separately before provider dispatch, during streaming, after a valid call is prepared, during a tool wait, and immediately around local commit. Prove no new commit for cancellation ordered before the mutation point, abort propagation to owned work, and quiescent settlement. Cancellation after a durable commit cannot undo that fact: record the committed operation/receipt and reconcile by K, rather than displaying 'no change' or retrying with a new key. Late chunks/results must not restore a cancelled UI state or cross an account switch. The upstream declarative tool `timeoutMs` does not enforce a deadline without its timeout policy; inspect the actual composition and run the deadline case.

Do not induce real paid quota exhaustion, invalid provider requests, or repeated provider failures for this initial assignment. Later authorized real-call evidence validates the happy path; deterministic negative cases remain explicitly CONTROLLED_FIXTURE unless separately exercised against a real provider. No model fallback, provider override, or reliance on this assistant's model identity is permitted.
