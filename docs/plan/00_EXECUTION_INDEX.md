## 3. 单功能开发循环

读取当前任务与真实代码 → 明确范围和接口 → 测试角色先定义可观察预期 → 唯一实现者开发 → 在固定候选版本实际测试 → 根据失败返修 → 独立复核 → 记录提交和结果 → 停止并交接。

同一功能内可以连续完成这些步骤，不需逐步等待用户。完成/受阻后不自动激活下一个功能，这是用户明确选择的分段执行方式。外部阻塞只允许继续本单元内独立部分，不允许转入未激活单元。

主管、架构、实现、测试角色是本次开发的组织方式；产品 F38/F39 中的智能讨论功能是后续业务能力，不能混同或因为有开发子智能体就宣称它已完成。

## 4. 通过的含义

文档检查只能证明结构与追踪一致；单元测试证明其覆盖逻辑；真实 DSH 端到端验证证明对应接入路径；Windows 安装和真实模型须各自证据。每个结论绑定代码提交/工作树指纹、环境、命令、输入和结果。

`work_units.json` 中 `acceptance_ids` 可以对应基础子场景，`final_acceptance_ids` 才是完整场景归属。单元通过后只更新该单元的已测内容；需求只有全部关联必要完整场景通过才能 verified。`NOT_RUN`、`BLOCKED`、`FAIL` 不算通过。
