# 分段实施与逐功能测试计划

执行规则修订：3.1.1，2026-11-16（Asia/Shanghai）。当前执行引擎是 **Codex**，当前只修复已实现 FND-003 身份切片并复验。本文件是未激活的工作目录和依赖说明，不是授权执行全部目录的提示词。唯一当前执行提示词在 [CODEX_START.md](../../CODEX_START.md)，当前激活单元以 [execution_state.json](../../config/execution_state.json) 为准。

## 1. 执行方式已经调整

采用“用户激活一个单元 → 澄清该功能范围与层次 → 同时制定测试 → 实现 → 实跑测试 → 独立复核 → 形成提交与报告 → 停止”的方式。一个功能不过关就修复这个功能，不能用进入下一功能掩盖失败。无外部阻塞时，在当前授权单元内完成开发、测试与返修，不反复追问常规实现细节。

任何时刻只有一个 `active_unit`、一个实现者负责该单元的代码写入。架构核对、测试设计、代码审查可以围绕这个单元并行；禁止多个智能体同时开发不同业务功能，禁止以分支或子智能体绕过当前范围。测试者可在约定测试文件范围工作，变更仍由同一整合负责人检查，不允许两个实现者互相覆盖。

M0–M6 只表示宏观归属。不能把“开始 M0”解释为本轮允许把 M0 全部功能开发完。当前仅 **FND-003：注册登录与个人身份**；FND-001 面板与 FND-002 持久化已验收。复用真实 Host 与业务 SQLite，增加可信初始化、独立业务会话、本人偏好和个人空间；完整对象权限、六工作区、模型和安装包仍待对应单元激活。

当前单元完成或确实受阻后停止，给出本单元证据、问题与下一单元建议，等待用户激活。受阻时可以在当前范围内继续独立的检查或修复；不能自行跳到另一单元。该边界来自用户明确要求的分段执行方式。

## 2. 架构如何逐层落实

采用 [总体架构](03_ARCHITECTURE.md) 的模块化单体与 DSH 插件集成，顺序由功能依赖决定。每个功能只增加它需要的界面、应用服务、领域规则、持久化或 DSH 适配，不为尚未激活模块提前铺业务表、空 API 或大批页面。

FND-001 只接通“Client 面板 → Host 只读状态服务”。FND-002 再增加一项真实持久化。FND-003 再增加身份。FND-004 再增加对象授权与共享路由边界。后续资料、学习与协作均通过相同已验证层次扩展，避免不同智能体各自发明一套架构。

当前开发用的主管/架构/实现/测试等角色，与未来产品的“DeepSeek 主 Agent + 评审投票”功能不同。开发协作使用 Codex 当前真实可用的智能体能力；产品主 Agent 的配置在相应功能单元实现，不能把本阶段开发工具的模型身份写成产品模型已经接通。

## 3. 每个单元必须先有测试再收口

1. 主管确认激活 ID、需求 ID、允许改动和排除范围，发给各角色同一版本的任务材料。
2. 架构角色给出复用点、层次依赖、数据/权限/失败边界；若新增组件无法由当前需求解释，删去该设计。
3. 测试角色在实现前给正常、边界、错误、恢复场景及明确预期；测试可以随实现细化，但不能事后改预期为失败开脱。
4. 实现角色按纵向闭环改动，完成可运行代码后执行匹配的类型/构建和行为检查。
5. 独立测试/审查角色从实际命令、状态和产物判断结果，不能照抄实现者的“已完成”；缺环境记受阻，未跑记未运行。
6. 修复该单元问题并重跑受影响检查，保留首次失败与最终结果。修复不等于扩大范围开发下个功能。
7. 主管核对差异只属于本单元、没有旧指令冲突和伪通过，更新进度与证据，提交可审查结果后停止。

测试粒度随功能：只读面板需要真实挂载、响应来源、错误与生命周期检查；持久化功能需要重启与事务回滚；权限功能需要多身份越权；有外部模型或平台的功能需要真实连接证据。既不为简单改动机械堆测试，也不把权限、数据和恢复检查推迟到最终全面审查。

## 4. 三种完成状态不能混用

- **工作单元收口：** 当前功能切片完成，自己的测试和复核通过。
- **完整场景 PASS：** 66 个原有验收之一真正全程运行通过，不是基础子场景或模拟替代。
- **需求 verified：** 该 F 需求的全部必要完整场景通过并有证据。一个单元通过通常不足以证明整项需求通过。

机器可读分解在 [work_units.json](../../config/work_units.json)。`acceptance_ids` 记录关联场景，`final_acceptance_ids` 指定完整场景最终负责单元；完整场景仍遵守 [验收矩阵](07_ACCEPTANCE_MATRIX.md) 的 `final_milestone`。例如 FND-001 只形成 F01/F04 的接入基础证据，以及 A01/A50 的局部证据。完整 A01 在身份与真实业务调用可用后的 FND-005 验证；完整 A50 在 CHECK-001 验证。当前单元通过不能把这四项全部标为通过。

工作单元设为 `passed` 时，同时保存 `evidence_paths` 指向真实运行与独立复核记录；执行状态改为 `awaiting_user`，保持当前 active_unit 不变。

每个单元的本地测试有独立稳定 ID，形如 `FND-001-T01`。这些单元测试编号不替换 P01–P14 或 A01–A52，也不增加用户需求。

## 6. 激活时只读取当前功能材料

主管先读取执行状态中的 active_unit，再按该 ID 从 work_units.json 提取唯一条目。只为检查前置条件查看 depends_on 对应单元的完成证据；不要把 76 个单元的详细范围和测试一次性塞入主管或子角色提示上下文。完整目录用于规划和覆盖审查，不作为本轮的隐含待办。

未来单元目前每项列出的两条测试义务仅是规划基础，不代表两条就足够验证整个功能。该单元被用户激活时，需要根据实际接口、数据、权限、失败恢复和关联完整验收，把测试细化到可执行操作、明确断言、测试环境和证据要求；必要时增加测试。FND-001 的七项、FND-002 的九项保留已验收历史；当前 FND-003 v3.1.1 在唯一提示词第 8 节与 JSON 中对齐十二项必测，编号 FND-003-T01 至 FND-003-T12。

激活下一单元时更新 JSON 中该单元的详细任务记录和唯一当前提示词，其他未激活单元仍是规划。发生用户需求变更时，检查受影响依赖和验收映射；不要以复制一份带版本号的新提示文件的方式保留两套有效指令。

当前 FND-003 继承已通过的面板、只读状态和真实磁盘持久化，在同一库增加原子 v2 身份迁移。十二项测试覆盖初始化、三个身份、DSH 权限分离、会话、来源保护、偏好、输入、迁移、回滚、资源限制、页面和构建回归。旧 FND-001 禁 DB 与 FND-002 两表/v1 检查保留各自历史候选；本轮新增准确的身份范围检查，不把历史限制改成当前假通过。

JSON 与当前提示词若出现测试编号、范围或期望不一致，主管先记录具体差异并停止冲突操作；不能自行挑选更容易通过的一套。本页索引发生差异时，以当前经核验的执行状态、唯一提示词与具体工作单元记录联合核对，按用户确定的范围修正。
