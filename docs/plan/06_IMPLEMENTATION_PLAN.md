# 分段实施与逐功能测试计划

当前单元由 config/execution_state.json 唯一指定；依赖与候选门禁见 CODEX_START.md。

## 1. 执行方式已经调整

采用“调度一个依赖已通过单元 → 澄清该功能范围与层次 → 同时制定测试 → 实现 → 实跑测试 → 独立复核 → 形成提交与检查点 → 调度下一单元”的方式。一个功能不过关就修复这个功能，不能用进入下一功能掩盖失败。无外部阻塞时，在当前授权单元内完成开发、测试与返修，不反复追问常规实现细节。

任何时刻只有一个 `active_unit`、一个实现者负责该单元的代码写入。架构核对、测试设计、代码审查可以围绕这个单元并行；禁止多个智能体同时开发不同业务功能，禁止以分支或子智能体绕过当前范围。测试者可在约定测试文件范围工作，变更仍由同一整合负责人检查，不允许两个实现者互相覆盖。

M0–M6 只表示宏观归属，不能据此自动激活其他单元。

当前单元完成或确实受阻后记录检查点；按依赖切换，不改变受阻者状态。

## 2. 架构如何逐层落实

采用 [总体架构](03_ARCHITECTURE.md) 的模块化单体与 DSH 插件集成，顺序由功能依赖决定。每个功能只增加它需要的界面、应用服务、领域规则、持久化或 DSH 适配，不为尚未激活模块提前铺业务表、空 API 或大批页面。

FND-001 只接通“Client 面板 → Host 只读状态服务”。FND-002 再增加一项真实持久化。FND-003 再增加身份。FND-004 再增加对象授权与共享路由边界。后续资料、学习与协作均通过相同已验证层次扩展，避免不同智能体各自发明一套架构。

当前开发用的主管/架构/实现/测试等角色，与未来产品的“DeepSeek 主 Agent + 评审投票”功能不同。开发协作使用 Codex 当前真实可用的智能体能力；产品主 Agent 的配置在相应功能单元实现，不能把本阶段开发工具的模型身份写成产品模型已经接通。

## 3. 每个单元必须先有测试再收口

1. 主管确认激活 ID、需求 ID、允许改动和排除范围，发给各角色同一版本的任务材料。
2. 架构角色给出复用点、层次依赖、数据/权限/失败边界；若新增组件无法由当前需求解释，删去该设计。
3. 测试角色在实现前给正常、边界、错误、恢复场景及明确预期；测试可以随实现细化，但不能事后改预期为失败开脱。
4. 实现角色按纵向闭环改动，完成可运行代码后执行匹配的类型/构建和行为检查。
5. 独立测试/审查角色从实际命令、状态和产物判断结果，不能照抄实现者的“已完成”；缺环境记受阻，未跑记未运行。
6. 修复该单元问题并重跑受影响检查，保留首次失败与最终结果。修复不等于扩大范围开发下个功能。
7. 主管核对差异只属于本单元、没有旧指令冲突和伪通过，更新进度与证据，提交可审查结果并保存检查点。

测试粒度随功能：只读面板需要真实挂载、响应来源、错误与生命周期检查；持久化功能需要重启与事务回滚；权限功能需要多身份越权；有外部模型或平台的功能需要真实连接证据。既不为简单改动机械堆测试，也不把权限、数据和恢复检查推迟到最终全面审查。

## 4. 三种完成状态不能混用

- **工作单元收口：** 当前功能切片完成，自己的测试和复核通过。
- **完整场景 PASS：** 66 个原有验收之一真正全程运行通过，不是基础子场景或模拟替代。
- **需求 verified：** 该 F 需求的全部必要完整场景通过并有证据。一个单元通过通常不足以证明整项需求通过。

机器可读分解在 [work_units.json](../../config/work_units.json)。`acceptance_ids` 记录关联场景，`final_acceptance_ids` 指定完整场景最终负责单元；完整场景仍遵守 [验收矩阵](07_ACCEPTANCE_MATRIX.md) 的 `final_milestone`。例如 FND-001 只形成 F01/F04 的接入基础证据，以及 A01/A50 的局部证据。完整 A01 在身份与真实业务调用可用后的 FND-005 验证；完整 A50 在 CHECK-001 验证。当前单元通过不能把这四项全部标为通过。

工作单元设为 `passed` 时，同时保存 `evidence_paths` 指向真实运行与独立复核记录；将独立结果与候选绑定后按依赖选择下一单元。

每个单元的本地测试有独立稳定 ID，形如 `FND-001-T01`。这些单元测试编号不替换 P01–P14 或 A01–A52，也不增加用户需求。

## 6. 激活时只读取当前功能材料

主管先读取执行状态中的 active_unit，再按该 ID 从 work_units.json 提取唯一条目。只为检查前置条件查看 depends_on 对应单元的完成证据；不要把 76 个单元的详细范围和测试一次性塞入主管或子角色提示上下文。完整目录用于规划和覆盖审查，不作为本轮的隐含待办。

未来单元目前每项列出的两条测试义务仅是规划基础，不代表两条就足够验证整个功能。该单元被选择时，需要根据实际接口、数据、权限、失败恢复和关联完整验收，把测试细化到可执行操作、明确断言、测试环境和证据要求；必要时增加测试。FND-001 的七项、FND-002 的九项保留已验收历史；历史 FND-003 v3.1.1 在唯一提示词第 8 节与 JSON 中对齐十二项必测，编号 FND-003-T01 至 FND-003-T12。

激活下一单元时更新 JSON 中该单元的详细任务记录及执行状态，入口正文保持稳定。发生用户需求变更时，检查受影响依赖和验收映射；不要以复制一份带版本号的新提示文件的方式保留两套有效指令。

历史 FND-003 继承已通过的面板、只读状态和真实磁盘持久化，在同一库增加原子 v2 身份迁移。十二项测试覆盖初始化、三个身份、DSH 权限分离、会话、来源保护、偏好、输入、迁移、回滚、资源限制、页面和构建回归。旧 FND-001 禁 DB 与 FND-002 两表/v1 检查保留各自历史候选；本轮新增准确的身份范围检查，不把历史限制改成当前假通过。

JSON 与当前提示词若出现测试编号、范围或期望不一致，主管先记录具体差异并停止冲突操作；不能自行挑选更容易通过的一套。本页索引发生差异时，以当前经核验的执行状态、唯一提示词与具体工作单元记录联合核对，按用户确定的范围修正。

### 8.4 DeepSeek 阻塞的解除路径

[已有预检](../evidence/FND-005/continuous/discovery-blocked.json)记录：隔离 DSH_HOME 缺少已配置的原生 web profile，发现流程在 Host 启动与路由解析之前退出，实际模型选择为零。它不能证明 API 无效、额度耗尽或业务工具实现失败，也不能证明最新候选已经完成真实调用。

先在当前候选核对固定 DSH、原生 profile、实际加载插件指纹、可用 provider/model 与既有凭据引用。使用支持的配置方式准备隔离测试环境，不整库复制个人凭据、会话或历史安装；旧插件成功结果不可作为新候选证据。已授权配置在当前环境可访问时，常规准备与复验继续执行；确实缺用户控制的信息时，只询问所需的测试 profile/Host、非敏感路由标识或安全配置方式。

需要用户提供的信息应具体，例如：“可以使用哪一个已授权 DeepSeek 测试 profile/Host？请在 DSH 原生凭据界面完成绑定，并提供不含密钥的 provider/model 标识。”不要求把密钥粘贴到聊天或 Git，不自行购买额度、切换供应商或复制私人数据。

环境可用后，FND-005 在当前冻结候选上执行真实读、受控写、重新读取，核对 UI/HTTP/SQLite、revision、幂等和权限，再由独立角色复验。全部 T01–T09 及 A01 的实际义务满足后才能关闭阻塞；未知费用记未知，保留现行费用展示/警示语义，不通过本计划新增硬性预算规则。

若 FND-005 一直阻塞，当前显式依赖图允许再推进的上界为 16 个单元：READ-002/003、SEARCH-001、LIB-006、SHARE-001、NOTE-001/002/003、LEARN-004、REPO-001/002/003、PROJECT-001/002/003/004。加上现有 11 个，最多 27/76；另 49 个包括 FND-005 本身及 48 个直接/间接受影响单元。此数是依赖上界，不保证外部样本、平台或全部场景条件就绪。记录阻塞解除条件；无条件变化时不反复消耗调用重试。

### 8.5 单元验收与跨单元补验

单元 PASS 证明本切片；完整场景 PASS 证明实际整链；需求 verified 要求全部关联必要场景通过。一个责任单元可以先完成切片，完整场景在真实所需组件具备后补验。不得为让场景提前通过而放宽断言，也不得把未来组件反向加为单元依赖造成循环。

已发现的补验安排：

| 场景 | 早期责任单元 | 补验触发条件 |
|---|---|---|
| P08 预审、终审与日评分 | PROJECT-002 | SCORE-001 的真实结算路径具备后，补验预审不提前计分、终审按真实提交时间结算 |
| A16 长期反馈不过期 | FEEDBACK-001 | LIFE-001 的真实清理具备后，验证跨 31 天的正常记录不被回收站策略删除 |
| A46 撤权阻断全部缓存路径 | LIFE-004 | EXPORT-001 具备后，补验搜索、直接 URL、工具、摘要、答案和导出全部受控路径；不把 EXPORT-001 反向设为 LIFE-004 的单元依赖 |

P01 的今日计划学习快捷入口已经属于 UI-001 的范围，不机械等待整个 PLAN-001。A04 激活时核对 FND-004 已有真实项目与 NOTE-001 的笔记引用能力，不因出现“项目”二字就强加全部项目管理模块。A19 要核对真实三平台读取及 AI 请求推送的拒绝；可使用已有受控模型入口验证，缺该入口时保留对应断言未完成，不能仅凭无写接口就声称已实测 AI 路径。

现有 `scripts/verify-plan.mjs` 对完整场景证据要求 `run.candidate_sha === owner.candidate_commit`。这不阻止单元先通过，却会让后期包含新组件的补验候选无法匹配早期责任单元的旧候选。应在首个需要跨单元补验的场景收口前，完成以下有针对性的门禁修正；它不成为 READ-002 业务实现的新增前置功能：

- 单元候选与历史证据保留；完整场景绑定自己实际执行的集成候选、构建及参与单元映射。
- 仍只有一个最终责任单元；责任单元和该场景全部必需组件必须通过。候选必须包含所用实现，并有受影响回归、实际命令/退出码、完整结果与独立复核。
- 提交继承关系只能证明包含历史提交，不能证明后来未改坏相应路径；应结合当前源码/构建指纹及必要回归验证。
- 补充能拒绝错候选、漏组件、借用旧证据、未运行/失败冒充 PASS 的门禁回归；不能仅删除 SHA 校验，也不能为了对齐 SHA 改写旧验收记录。
- 继续保留 76 单元、44 需求、66 场景和原业务断言。场景的责任归属阶段不等于所有所需组件已经齐备；实际触发条件以完整场景的真实前提为准。

该修正是后续待实施事项，本次只更新规划说明，没有宣称门禁代码已修复。

### 8.6 持续开发的记录与最终完成

每轮按“当前单元实现和测试 → 修复 → 冻结候选 → 独立复核 → 更新三个层级的状态 → 推送并回读 → 选择下一单元”推进。在同一功能内并行做范围/架构核对、测试设计和审查；共享 schema、领域状态和生产代码串行整合。共享依赖有变化时做对应回归，普通小改不重复跑全仓库或重复下载全部环境。

完整场景所需组件就绪时，立即安排上述补验；候选冻结后的验证期间暂停生产代码改动。不得把“单元已通过”误当“相关场景永久有效”：后续权限、定位、迁移、计分或队列修改影响已通过行为时，需要重跑对应路径并保留新结果。

进度摘要分别报告工作单元、完整场景、完整需求、真实 DeepSeek 和 Windows 交付。每个检查点保存候选、构建指纹、当前单元、实际测试、缺陷、待补场景、阻塞解除条件及下一可执行任务。历史失败与原始证据保留；现行说明与机器状态保持一致。

完成定义：76 单元已通过、66 场景在适用候选上有真实完整证据、44 需求可追溯且 verified；六工作区和 A52 真实链路贯通；DeepSeek 实测、权限/版本/个人表现、异常恢复、备份恢复及 Windows 安装/升级/回退/卸载均具备证据，且无阻断缺陷。CHECK-004 范围内的全面审查、修复和最终回归属于现有持续开发授权，不为常规收口再次请求“是否继续”。外部必需条件缺失时明确报告剩余项，同时继续安全独立工作。

公共发布、生产部署、真实数据破坏、受保护分支合并及新增费用仍遵循根指令的询问边界。项目完成后不自动扩大到新需求或新的外部发布动作。
