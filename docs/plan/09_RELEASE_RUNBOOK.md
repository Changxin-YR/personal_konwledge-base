# 构建、安装、运行与发布

当前尚无 KnowledgeOS 安装包。本页定义未来发布单元的交付要求；仅在对应单元由用户激活后执行。当前 DeepSeek Harness 的 FND-002 只完成本地持久化切片，不构建安装包；后期 Codex 全面审查是另一阶段。命令必须匹配当次锁定源码与实际产物。

## 1. 开发准备

克隆用户仓库，先读 AGENTS 与唯一当前指令 DSH_START.md。源代码准备脚本只拉取固定官方提交；不替用户更新全局 DSH、不扫描个人电脑中其他项目、不安装未知 ASAR。

```sh
git clone https://github.com/Changxin-YR/personal_konwledge-base.git
cd personal_konwledge-base
node scripts/verify-plan.mjs
node scripts/prepare-upstream.mjs --check
node scripts/prepare-upstream.mjs --prepare
```

上游要求 Node >=24.9.0、pnpm 11.28.5。脚本会检查 Node/Git 与检出版本；pnpm、依赖与目标打包环境由 M0 实际安装/检查，不宣称脚本替代完整环境配置。

固定上游的支持命令包括 `pnpm install`、`pnpm run build:artifacts`、`pnpm run build:check`、`pnpm dsh web`。依赖安装优先使用与上游锁文件兼容的冻结模式；失败时先分析版本/网络/原生依赖，不能直接删锁文件重算。构建命令在上游检出目录执行，不能在尚无 package.json 的本仓库根目录假装运行。

本项目的最终开发命令、插件本地安装命令和 profile 参数由 M0 验证后写入 README。上游支持本地 checkout 的 `dsh plugin --profile <name> add <path>`，但 Client 必须先产出 DSH 模块格式，不能只安装 TypeScript 源码。开发缓存与成品安装所需闭包必须分别检查。

## 2. 三种交付形态

| 形态 | 用途 | 应交付内容 |
|---|---|---|
| KnowledgeOS Windows 桌面候选包 | 用户日常使用，第一优先 | 安装程序、内置正确 DSH runtime、KnowledgeOS 插件/客户端/配置、许可说明 |
| KnowledgeOS 插件/Bundle 包 | 开发与已有兼容 DSH 用户 | 构建后的 tarball、兼容 SHA/版本、安装/卸载方法、已知限制 |
| 协作服务部署包 | 约十人共享空间 | 专用服务配置、数据库/文件目录规则、HTTPS 接入、运行/备份/恢复脚本 |

桌面使用独立应用 ID、名称、安装路径和 userData/DSH_HOME，不能覆盖用户已有 DSH 或公司 Mandate。品牌与安装 profile 的纯配置可行性在对应桌面/发布单元验证；必要的薄补丁单独记录，禁止篡改上游许可证与版权。

## 3. Windows 构建

固定上游包含 `pnpm run package:desktop:win:x64:unsigned` 与签名构建路径；具体前提见该提交的 [Desktop README](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/apps/desktop/README.md) 与 [Windows signing README](https://github.com/deepseek-ai/deepseek-harness/blob/39163dd30f703a79079e2d2446545cff3c453738/apps/desktop/windows-signing/README.md)。这些命令构建上游应用；KnowledgeOS 必须先完成自己的品牌、配置、插件与运行时闭包装配，才能称为产品安装包。

有签名环境则按可用凭据签名；没有签名材料可以继续产出明确标注 unsigned 的候选包用于测试，不伪造发布者，不关闭系统防护。只支持并实测的架构才出包，不能凭文件名宣称 ARM64 兼容。

必须在实际安装后的 Host 检查 `node:sqlite`、文件转换依赖和插件 Client 模块加载。源码开发成功不代表 ASAR/打包资源路径、权限、ABI 和可写目录正确。

## 4. 安装与升级验证

| 场景 | 需要看到的证据 |
|---|---|
| 干净安装 | 安装完成、正常启动、产品首页、应用版本与数据目录 |
| 首次使用 | 创建身份/配置规划时段、资料导入、保存后重启仍在 |
| 二次启动 | 不重复初始化管理员、数据迁移或提醒 |
| 版本升级 | 备份成功、迁移记录、旧资料/笔记/作答/任务仍关联正确 |
| 升级中断 | 可判断迁移状态、可以恢复，不静默清库 |
| 应用回退 | 旧版 schema 兼容性检查；不兼容时用一致备份恢复或提供前向修复 |
| 卸载 | 默认保留个人数据；清理数据需明确说明影响和具体操作 |
| 多次安装/并存 | 不占用别的 DSH 数据目录，不用同一应用 ID 覆盖其他产品 |
| 断网/休眠恢复 | 已保存数据不丢、待操作核实、提醒重新计算且不补发积压 |

Windows 虚拟机、隔离机器或用户明确授权的测试环境均可。没有这样的环境时，记录哪些平台检查已完成、哪些仍未运行；不能把打包成功、Wine 或 Linux 测试当作 Windows 原生完整安装验收。

## 5. 协作部署

服务端单写自己的本地数据库与对象目录，成员不直接挂载 SQLite 文件。首次管理员引导只允许在受控本机完成；不提供默认共享密码。对外地址使用 HTTPS，登录会话和邀请有到期与撤销；配置错误拒绝启动并给可操作说明。

桌面原生 Host 保持 loopback。共享服务暴露的只有 KnowledgeOS API 与必要静态资源；提供路由清单，证明通用 file/session/shell/plugin 管理入口不可被普通成员访问。服务日志不含密码、邀请原值、模型密钥或私人正文。

服务可运行并不意味着有人持续在线：管理员电脑休眠后共享操作会等待。界面准确显示连接和待同步状态。需要全天可用时迁到已有常开机器，迁移遵循备份/恢复流程，不默默把数据传到新云服务。

## 6. 备份、恢复与回退

使用 SQLite 一致性备份方案或协调短暂停写，不能只复制正在变化的 `.db` 而漏 WAL。manifest 记录 schema、服务 ID、应用/上游版本、数据库/对象哈希、备份时间和范围。源文件、版本、提交与关联关系必须一致。

索引可重建，但备份记录其构建版本；恢复后重建前不能查询到旧租户索引。模型密钥与登录会话按单独安全配置处理，不默认放进普通导出。历史被撤销/过期授权不因备份较旧自动复活；恢复时按当前时间和撤销策略复核。

先验证备份完整性，在新目录试恢复并预览冲突、服务身份和权限影响，再替换权威实例。恢复测试包括打开原页、错题归属、管理员终审、投票版本、评分修正和提醒账本。旧实例与新实例不能同时作为同一规划归属的权威写入者。

## 7. 发布到本仓库

源码、实施方案、变更记录与脱敏证据提交到 Git；安装程序、插件 tarball 和软件构建/源码交付包放本仓库 **GitHub Releases**。用户资料导出、运行数据库、教材和备份不得上传公开 Releases。不将大二进制直接提交进 Git 历史。

候选版本使用独立 KnowledgeOS 版本，如 `v0.1.0-rc.1`，标为 prerelease；上游版本单独记录。发布说明至少包含：

- 本项目提交与上游完整 SHA、目标平台/架构、是否签名。
- 资产名称、字节数、SHA-256、下载链接。
- 实际完成的功能、真实运行验证、仍受阻的项目。
- 安装/升级步骤、数据目录、备份与恢复方法。
- 许可与第三方依赖说明。

`releases/index.json` 只记录已经实际生成且校验过的资产。无包时保持空数组；无上传权限时保留本地产物与可执行发布步骤，报告“未上传”，不填虚构下载地址。开发候选版本可以按已授权开发工作发布；正式稳定发布和最终合并留给用户审核。
