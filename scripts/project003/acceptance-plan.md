# PROJECT-003 独立验收预期

依据需求 F34/F35、工作单元 T01/T02、业务状态契约 §7 和完整场景 A32。先据此写 runner，再对冻结候选使用真实 DSH Host、独立 Chrome context 和 SQLite。所有身份、项目、任务和材料都是隔离合成数据。记录候选提交/树、产物和 runner 哈希、命令、实际 HTTP 状态、SQLite 对照、Chrome 状态及截图。主跑与独立复跑分别启动新 Host 和新数据目录。

## 准备

1. 通过真实注册登录获得普通项目 owner、负责人、指定普通审核人、另一成员。通过真实 owner bootstrap 生成业务管理员。普通 owner 通过产品建项目、发成员邀请，并使用候选所提供的明确项目授权为管理员开放纠正。管理员在另一普通 owner 的非授权项目中作对照。全部使用不同 Chrome context。
2. 创建两个验收项目，一项普通协作任务和一项现有管理员任务回归。普通 owner 在项目页面给负责人派发，选普通指定审核人，固定截止时间和标准。记录任务、初始 revision、标准版本及候选实际时间来源。必要时用现有隔离时钟重放时间边界。

## T01 普通任务的指定审核人

1. 负责人从项目页面提交，SQLite 保留真实接收时间、标准版本及提交 ID。任务为“待审核”，下一处理人为指定审核人。负责人、非指定普通 owner、另一成员和管理员都无法提交初始裁决。用同候选真实 UI 检查操作入口，并从独立 HTTP 会话请求相应动作。每个拒绝都检查错误编码和零写入。
2. 令审核时间晚于期限。指定普通审核人从 Chrome 按提交时固定标准逐项填写结果和原因并通过。确认真实 HTTP 创建、页面展示生效结论以及 SQLite 的审核人、提交 ID、阶段、标准依据、原因和时间。提交时间、准时性及标准版本保持原值，任务状态完成且下一处理人为空。
3. 对普通任务选用同伴预审动作应拒绝。对管理员任务，指定同伴通过后仍应等待管理员终审。其他成员调用终审仍拒绝。重复运行既有初始审核回归，保留原先分页、返回或续接等历史断言。

## T02 管理员纠正、并发和重试

1. 从有当前项目授权的管理员页面打开普通任务，确认可见原裁决。发起纠正前保存 SQLite 基线，至少含任务 revision、原提交及原裁决各列。用缺理由、无权成员、普通 owner、未获该项目授权的业务管理员以及本人是提交负责人的管理员试纠正，记录权限拒绝与零新增裁决。
2. 保留一页的旧 revision 和原裁决 ID。由管理员用页面完成一次更正，将通过改为失败，填写逐项原因和纠正理由。HTTP 成功后，负责人和管理员看到原裁决、替代裁决、不同裁决 ID、旧决定关联和新理由。SQLite 原裁决逐列等于基线，任务 revision 恰加一，任务状态未通过、下一处理人为空，提交 ID、接收时刻、准时性及标准版本均保持。对其他项目 ID 和旧提交 ID 的纠正要拒绝。
3. 在第二条普通任务上，让两个不同幂等键的纠正请求携带同一任务 revision 和同一被替代裁决，真实并发发出。只能一个成功，其余返回 409，核对恰有一条新增裁决。用获胜请求的同键同参重放，拿到同一裁决 ID 且无新的 revision 或记录。用同键修改理由或结论须 409。用新键提交旧 revision 或以最新 revision 纠正已替代的旧裁决也须 409，仍无写入。
4. 在隔离实例撤销管理员的项目资格，复读、纠正和重放均失权。另一真实项目页面仍可正常使用。重启实例后从全新 Chrome context 登录负责人并核对原与新裁决、理由和最新状态。记录 SQLite 外键检查和实际行数。已有固定材料审查在此候选应回归，材料可见权限和纠正权限分别核对。

本单元验证普通审核与直接纠正。完整 A32 还需 PROJECT-004 的真实用户复议与处理路径，先保持 NOT_RUN。
